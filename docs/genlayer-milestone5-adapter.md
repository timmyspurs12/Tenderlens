# Milestone 5 — application-level contract input binding and runtime qualification

## Baseline and lifecycle audit

This work began from clean branch `arena/a72eb9de-tenderlens` at `51121d5ff34f9251bc1f48c116938d9f1f95d766`. The Milestone 4 preflight was reproduced on the local CPython 3.11.2 host and reported 9 blockers. Existing backend API, policy, frontend, and Direct Mode behavior were inspected before editing.

Before this milestone the lifecycle stopped at `POST /evaluation-snapshots` -> immutable payload in SQLite -> authenticated GET. Direct Mode tests manually passed a GET response into `direct_deploy`; there was no request ledger, submission adapter, network call, or result ingestion. The contract's constructor takes exactly one JSON string and its output echoes `evaluation_id`, `snapshot_id`, `snapshot_sha256`, and policy. It does not accept a backend signature, a request ID, or a transaction reference.

## Implemented adapter boundary

`backend/evaluation_adapter.py` adds an internal Python integration boundary; it does not add or change a public HTTP endpoint or frontend behavior. `EvaluationAdapter.prepare(snapshot_id, idempotency_key, expected_policy)` accepts no payload argument. It:

1. Finds the row inside the API's configured workspace and obtains its payload through the same authenticated `evaluation_snapshots(... GET ...)` path used by snapshot retrieval. That path verifies the stored HMAC, row identity, embedded snapshot ID, stored digest, and recomputed canonical digest.
2. Rejects missing/invalid IDs, failed row verification, unsupported submission schema, malformed required submission structures, unsupported or unexpected policy version, and optionally stale snapshots (`max_snapshot_age`).
3. Returns the exact stored `payload_json` string as `contract_input_json`. It does not reconstruct or reserialize client-provided data, preserving the exact payload/digest relationship.
4. Creates a durable request record containing request ID, unique snapshot ID, digest, policy version, state, timestamps, and later contract address, deployment transaction hash, evaluation transaction hash, result JSON, and result reference. No evidence payload or secrets are copied into logs.

`EvaluationAdapter.submit(..., submitter=...)` is the normal application submission port. It calls the injected runtime-specific submitter only with the verified exact constructor JSON plus non-evidence request metadata. It atomically claims one submission attempt before the external call. Repeating an idempotency key returns the existing request without invoking the submitter again. A snapshot can have only one request; a fresh evaluation requires a fresh snapshot. If the process exits with state `submitting`, retry is deliberately blocked as outcome-unknown; an operator/runtime-specific reconciliation is required rather than risking a duplicate transaction. No automatic reset to prepared is offered.

The submitter must return the real contract address, deployment transaction hash, and evaluation transaction hash, which are shape-checked, persisted, and immutable after first association. `accept_result` requires the associated contract address and evaluation transaction hash, checks result schema plus evaluation ID, tender ID, snapshot ID, digest, and policy against the still-authenticated snapshot/request, then persists it idempotently. Conflicting/missing refs, a stale result from a different snapshot/transaction, modified source row, or conflicting retry fails closed.

### Deliberate limit: no live GenLayer driver

The repository still does not select a qualified target network/runtime or hold an authorized wallet. The adapter's `submitter` is an explicit integration port, not a fabricated SDK deployment. No production network call, mocked RPC, or actual transaction is made by ordinary tests. A runtime-specific driver must, using `genlayer-py==0.18.0`, obtain a finalized deployment receipt and actual contract address, write `evaluate`, wait for the appropriate finalized execution state, read `get_result`, and pass the result along with the real transaction reference. The pinned SDK documentation exposes `deploy_contract`, `write_contract`, `wait_for_transaction_receipt`, and `read_contract`; its e2e examples show that contract-address receipt paths differ by chain. That variation and the currently unqualified runner make a generic “successful” driver unsafe to invent here.

The adapter does not prove that a supplied receipt/result was actually fetched from GenLayer. `accept_result` is a trusted application ingestion boundary: the runtime driver must authenticate/fetch the result from the network before invoking it. A forged caller with access to that internal method could lie about references. The contract result schema has no evaluation request ID or transaction ID, so application association is by the single-request-per-snapshot ledger plus the stored contract/transaction refs and the echoed evaluation/snapshot/digest/policy values. Adding a request ID to contract state was avoided to preserve the existing schema. Direct contract callers can still deploy unrelated constructor data and bypass this adapter.

## Application protection versus contract enforcement

The adapter provides an application-path guarantee: if the trusted application calls `submit` with a snapshot ID, its submitter receives only that authenticated stored row's exact payload. It prevents substitution through this path and binds consumed results to the expected stored snapshot metadata and application-recorded transaction references.

This is **not** end-to-end on-chain integrity enforcement. The deployed contract remains publicly callable and checks digest shape only. A separate caller can construct different data with a digest-shaped or freshly recomputed value and call the contract directly. HMAC remains backend-local and is not shared with or verifiable by GenVM.

The pinned SDK and inspected GenLayer contract/runtime sources document off-chain account signing and transaction calls, but this audit found no documented contract-side verification interface for TenderLens signatures and no verified deployed runtime support for the required signature/hash primitives. GenVM manager/executor SHA-2 build material alone is not a Python `hashlib` runtime test. No shared secret, key, or homemade signature was introduced. Closing the on-chain gap requires a supported, target-verified cryptographic verification primitive and protocol: e.g. a documented signature scheme and public-key authorization/rotation policy, or an on-chain commitment/attestation mechanism whose inclusion and verifier semantics are established. This requires explicit design and negative tests; it is not claimed here.

## Adversarial coverage

`backend/test_evaluation_adapter.py` uses a real SQLite-backed `TenderLensAPI` and actual HMAC/digest checks; only the external submission port is synthetic. It covers valid exact payload binding, caller payload substitution (the adapter API does not accept payloads), altered payload with old digest, invalid HMAC, identity and missing snapshot IDs, policy mismatch, unsupported/malformed schema, digest inconsistency, stale snapshot age, idempotency key reuse/conflict, single-attempt claim, ambiguous submitter crash/no blind retry, missing/invalid/conflicting transaction refs, result identity/policy/transaction mismatch, stale result from another snapshot, and idempotent/conflicting result ingestion. Direct Mode continues to test that an independent constructor can bypass application checks; this remains a documented contract limitation. Existing tests continue to cover the two policies, evidence IDs/citations, malformed model output, and result references derived from submitted evidence.

## Runtime and dependency qualification

- Repository/runtime defect classification: Python 3.12 is already specified in the devcontainer and GenLayer setup, and SDK/test roots plus hashes/source revision are already in `requirements-genlayer.in`, `requirements-genlayer.lock.txt`, and the build lock. Milestone 5 pins Python 3.12 in both Actions jobs, checks the full SDK/test/pytest lock in preflight, runs preflight in the locked GenLayer CI environment, and adds the adapter tests to the ordinary backend job. The local Agent Mode host remains Python 3.11.2 and lacks GenLayer packages; this is an environment limitation, not a reason to alter dependency pins.
- Verified compatibility basis: `genlayer-py==0.18.0` source tag resolves to `cf421edc0d20e567cc5a3b4da198fce61f1e579f` and declares Python >=3.12. The locked Testing Suite source is `343e3a358f9e235a93b49c60721ce7676585ff07`, version 0.29.2, whose source metadata allows SDK 0.18.x. Its PyPI wheel metadata conflicts with SDK 0.18.x and remains intentionally excluded. The lock pins pytest 9.1.1. The GenLayer CLI remains neither installed nor pinned in this repo; the SDK is used as the documented client API and no CLI version is invented.
- Runtime qualification remains blocked: `py-genlayer:latest` is mutable. No exact immutable runner artifact verified against a selected target was found; the preflight reports an apparent GVM32 hash as informational only, not qualification. Direct Mode uses ordinary Python; its tests cannot substitute for a GenVM/WASM compilation or deployed-runtime smoke test. The SDK's `get_contract_schema_for_code` is documented localnet-only, and no supported target compiler/runner is provisioned in Actions. CI now verifies the locked Python environment and Direct Mode, and records that external deployment blockers remain; it does not claim WASM/deployed compatibility.
- Source review anchors: the pinned SDK's `genlayer_py/client/genlayer_client.py` exposes the deploy/write/read/wait methods used in the integration discussion; its pinned SDK reference documents signatures, while `tests/e2e/tests/test_user_storage.py` illustrates chain-specific receipt address paths. The SDK's crypto references are for off-chain ABI selector hashing/transaction signing and do not establish an Intelligent Contract signature-verification API. The M4 document records the exact GenVM manager/executor commits inspected; those sources did not verify callable Python `hashlib` in the network's runner.
- External prerequisites remain: select and authorize a specific target endpoint; verify its chain/network rather than just its chain ID; provide a protected authorized account; independently establish funding/fee budget; identify a target-supported immutable runner artifact; and run a matching GenVM/Studio smoke/compile path. The optional preflight RPC action performs only an explicit read-only `eth_chainId` request. No wallet balance check is implemented. No deployment or transaction is attempted.

## Preflight change and preserved behavior

The preflight now verifies the generated dependency lock includes the audited SDK, pinned upstream test source, and pytest. A GVM32-shaped runner reference is informational only (shape is not existence/compatibility evidence); selecting a network without a read-only RPC probe remains blocked. GitHub Actions runs the preflight in the exact locked GenLayer environment and asserts that Python/SDK/test/pytest prerequisites are satisfied while accepting external blockers. No secret values are printed. Runtime, authorization, and funding blockers are not papered over.
