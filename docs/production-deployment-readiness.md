# Production deployment readiness

This document records verified deployment state and remaining operator decisions. A static frontend is publicly deployed from merged `main`; the records API, persistence, authenticated browser workflow, and live GenLayer evaluation are not deployed or verified.

## Current application shape

- **Frontend:** React + TypeScript + Vite, built by `npm ci && npm run build` into `dist/`. `vercel.json` configures that static build and SPA fallback.
- **API:** Python 3.12 standard-library WSGI application in `backend/app.py`, with SQLite and content-addressed files on the local filesystem. `/healthz` is a public, minimal readiness check that runs `SELECT 1`; it reports no local paths or secrets.
- **Persistent data:** `TENDERLENS_DB_PATH` and `TENDERLENS_BLOB_DIR` must point to persistent storage on a backend host. Do not run a production instance on an ephemeral filesystem. SQLite and file storage are currently single-service/local-storage architecture; assess a managed database and object storage before multi-instance or higher-volume public service.
- **GenLayer:** the backend has a fail-closed SDK driver, environment-based fee/auth scopes, durable EVM/GenLayer transaction journaling, read-only preflight, and reconciliation. `create_app()` attempts local driver configuration and disables GenLayer routes if checks fail. This is not a qualified target or deployed contract: no live target/RPC, signer, funding, fee profile, or deployment has been verified.

## Public-service security blockers

The API authenticates every application request using the server-side `TENDERLENS_API_TOKEN`. The React SPA does not implement a login/session flow and its API client sends no bearer authorization. Never put that API token in a `VITE_*` variable or browser bundle. The current API also has no configurable origin allowlist or application-level rate limiter. Before exposing protected tender records, choose and implement an authenticated BFF/identity-aware gateway, use same-origin routing, and configure host-level rate limits and abuse controls. Do not make the backend token public to make the UI appear connected.

No identity provider, backend host, managed database, or object-storage service has been selected or connected. The Vercel account is connected and validated; a `tenderlens` project was created and its first production build deployed from merged `main` commit `e7c5ea95bb26053dc0b0d7e19ea5841bd40134b4`. Railway is not available as a connected-app integration; a backend host must be configured by its owner through an authorized dashboard or integration.

## Backend configuration names

Set backend values only in the backend host's encrypted environment/secret settings. Never put values in source, build-time frontend settings, commits, logs, or chat.

- Required service authentication: `TENDERLENS_API_TOKEN` (at least 32 characters).
- Workspace and persistence: `TENDERLENS_WORKSPACE`, `TENDERLENS_DB_PATH`, `TENDERLENS_BLOB_DIR`.
- Snapshot authentication: `TENDERLENS_SNAPSHOT_HMAC_KEY` (keep stable; set a separate value for production rather than relying on the API-token fallback).
- Runtime binding: `backend.app` now defaults to `0.0.0.0`, prefers the host-assigned `PORT`, and retains `TENDERLENS_HOST` / `TENDERLENS_PORT` overrides. This makes the WSGI entrypoint bind correctly on common PaaS platforms; it does not itself provide persistent storage, an authenticated browser session, or a hosted backend.
- GenLayer server-side settings are listed in `backend/genlayer_sdk_driver.py` and `scripts/genlayer_preflight.py`. Do not configure the private-key variable until an authorized wallet custody/signing method and production host are chosen. A broadcast opt-in flag is not signer authorization or a substitute for target/runtime/funding verifiers.

## GenLayer deployment gate

The official GenLayer docs repository at commit `7c3ad7c4bc738a7c55d05df780dd76c2cb052db6` (2026-10-20) documents `genlayer deploy --contract <path> [options]`, `--rpc`, and `--args`; it lists `testnet-bradbury` as the production-like testnet. The official npm package's current `latest` stable tag is `genlayer@0.39.2` (an RC tag also exists). In this Node 22.22.3 sandbox, an ephemeral `npx genlayer@0.39.2` run confirmed version `0.39.2`, the deploy syntax, and the built-in `testnet-bradbury` alias. Its static list also showed `testnet-asimov`, but the current stable network guide does not identify that as the recommended target, so it is not selected. A normal install failed while building optional native `keytar`; `--ignore-scripts --omit=optional` allowed help/version checks only and is not a secure signing setup. No global CLI or wallet was installed.

Official network docs publish Studionet at `https://studio.genlayer.com/api` (chain ID 61999) and Bradbury chain RPC `https://rpc.testnet-chain.genlayer.com` (chain ID 4221, currency GEN). Bradbury requires checking genesis hash `0x17d89764d4f4f963158fc4c5e8f2cb670c2837740b35f37081c12860c3df97e4` and AddressManager `0x3F71AE080BD6270A91dBcc7960d88797828538E0`; chain ID alone is not sufficient. Crucially, the docs distinguish the underlying GenLayer Chain RPC from the GenLayer node RPC needed for `gen_*` intelligent-contract methods: Bradbury's node RPC must come from the Phase 2 release announcement or a separately qualified node. We do not have that endpoint, and this environment cannot reach GenLayer RPC hosts. Therefore Bradbury is only the documented candidate, not a selected or verified target; published endpoint details are not live identity evidence.

The contract now pins `py-genlayer:1jb45aa8ynh2a9c9xn3b7qqh8sm5q93hwfp7jqmwsfhh8jpz09h6`, the exact runtime identifier in current official first-contract documentation. The previous Direct Mode suite (v0.29.2) failed to load even its minimal storage fixture with this runtime. The official v0.30.0-rc.2 Testing Suite source and genlayer-py v0.19.0-rc.2 add current GenVM manager bundle support, but CI reproduced an upstream `unexpected end of memory` message-injection bug (Testing Suite issue #113). A narrow test-only shim bypassed that failure, but the rerun still fails on a storage access because expected `__type_desc__` metadata is missing. Direct Mode/runtime compatibility is unresolved. A passing Direct Mode run would still prove only behavior in that test harness; it will not establish that current Studionet or Bradbury validators accept this exact runtime/contract. Before deployment, an authorized environment must verify target identity and supported runner, then execute a target-compatible compilation/contract test. This workspace's outbound policy does not permit requests to the GenLayer RPC hosts, so those live checks cannot be performed here.

Current official fee guidance treats fees as measured/profiled requirements and requires live estimation against current network price/cap data. The pinned genlayer-py v0.19.0-rc.2 SDK exposes fee-estimation helpers, but this workspace has not obtained a current target quote. No fee amount or reserve has been inferred. The driver now requires a measured, digest/scope-bound profile no older than seven days, fresh quotes for deployment and evaluation, outer EVM gas bounds, a configured total-cost cap, and an observed target-account balance sufficient for the full upper-bound cost. Missing fee components never become zero. These checks are safeguards, not evidence of a live quote or authorization.

The approved workflow is: read-only target identity and runner qualification; secure wallet creation and public-address review; exact fee quote and user approval; user funding through the official testnet route; balance verification; one deployment; finalized receipt, transaction hash/address verification using official network/explorer evidence; then a synthetic-data read/write check. Do not proceed past a gate if evidence is unavailable.
